# CAN-протокол, диагностика и обновление

## Разделение и скорости (предварительно)

| Сеть | Стартовая скорость | Задача |
| --- | --- | --- |
| ENGINE CAN | 500 кбит/с | ECM-IO, ECU, приборы, TCU/гибрид |
| BODY CAN | 250 кбит/с | BCM-F-IN, унифицированные BCM-F/R-OUT |
| HOUSE CAN | 250 кбит/с | устройства жилой зоны |
| AUX CAN | Не назначена | резерв/трансмиссия/отдельная силовая подсистема |

Скорости, конечные узлы, клеммы 120 Ом, длины магистрали, ответвления, загрузка и устойчивость к помехам проверяются на стенде и в машине. Классический CAN 2.0B — совместимый минимум. Два внешних MCP2518FD потенциально поддерживают FD, но **не** следует объявлять весь Gateway CAN-FD мостом.

## Сообщения (проектные имена, без закреплённых ID)

| Сообщение | Сеть/источник | Сигналы |
| --- | --- | --- |
| BODY_SWITCH_STATE | BODY, BCM-F-IN | запрос габаритов, ближнего/дальнего, поворотов, дворников |
| BODY_OUTPUT_STATE | BODY, каждый BCM-OUT | состояния, заданные/фактические токи, активные защиты |
| BODY_FAULT | BODY, каждый BCM | канал, причина, время возникновения, счётчик повторов |
| ENGINE_RPM | ENGINE, ECM-IO либо ECU | RPM, валидность, источник |
| ENGINE_COOLANT | ENGINE, ECU либо ECM-IO | °C, валидность |
| VEHICLE_SPEED | ENGINE, ECM-IO либо TCU | км/ч, valid, источник, счётчик |
| VEHICLE_DISTANCE | ENGINE, счётчик источника скорости | общий/суточный пробег по выбранной модели хранения |
| MODULE_STATUS | Все сети, каждый блок | ID устройства, версия, питание, watchdog reset, статус CAN |
| HOUSE_SENSORS | HOUSE, соответствующие блоки | баки, температуры, питание автодома |

Сделать каталог DBC и реестр уникальных ID/producer/consumer. **Не назначать окончательные ID до review требований**. Определить приоритет критичных кадров, цикл передачи, alive-counter, timeout, идентификатор версии протокола, признаки valid/stale и реакцию потребителя при их отсутствии. Приоритетные уровни и маски фильтров должны исключать перегрузку.

## Состояния вместо разовых команд

BCM-F-IN регулярно публикует состояние переключателей, а не только «нажал один раз». Выходные BCM восстанавливают предписанный режим после собственной перезагрузки. Правила fallback индивидуальны: габариты, дальний свет, дворники, стопы и аварийная сигнализация должны иметь отдельную логику, согласованную с safety-анализом. Ни отсутствие периодического кадра, ни включение питания не должны самопроизвольно активировать небезопасную нагрузку.

## Gateway whitelist

Разрешён только явный список сигналов между сетями. ENGINE → BODY/HOUSE: разрешённая телеметрия; BODY → ENGINE: при необходимости строго валидированные запросы не критичных функций; HOUSE → ENGINE: по умолчанию **никаких управляющих команд**. Незнакомые CAN-ID не пересылать, сетевой интерфейс ESP32 не предоставлять как бесконтрольный raw-CAN tunnel.

CAN узлы не аутентифицируются классическим протоколом CAN; для функций управления предусмотреть физическую защиту портов, сегментацию, контроль допустимых источников/счётчиков и архитектурную защиту от компрометации ESP32. Одних CAN-ID для криптографической проверки происхождения недостаточно.

## Диагностика

Слои:
1. Канал: обрыв/неожиданный низкий ток, short-to-ground, short-to-battery (если аппаратно различимо), температура, защита, напряжение.
2. Узел: watchdog resets, запуск/прошивка, питание, версия HW/SW, таймауты, bus-off, потерянные кадры/очереди.
3. Автомобиль: человекочитаемое сообщение с местоположением и стороной («левый задний стоп-сигнал»), журнал, отметка времени, действующая/историческая неисправность.

Коды ошибок (DTC) AVTOSTAR определить собственной таблицей; не выдавать их за заводской OBD DTC без соответствия стандартам.

## ESP32

Предоставляет защищённую локальную веб-панель состояния, журнал, карту узлов, сервисные процедуры. Основной режим по умолчанию — **только чтение**. Любые сервисные изменения и обновления прошивки — отдельный проверяемый канал с аутентификацией, режимами обслуживания, откатом, аппаратным запретом опасных действий во время движения. Отключение/перезагрузка ESP32 не влияет на штатные функции.
