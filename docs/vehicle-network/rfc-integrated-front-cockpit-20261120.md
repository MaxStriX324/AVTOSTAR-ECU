# RFC: единый передний кузовной/приборный модуль с двумя MCU

**Дата:** 2026-11-20. **Статус:** **альтернативы на обсуждении**, не утверждённая спецификация PCB и не замена предыдущей архитектуры.  
**Контекст:** владельцу не нравится отдельный AVTOSTAR CLUSTER; он предлагает объединить BCM-F-IN с приборной панелью, Gateway на STM32F405 с 4 CAN и, возможно, ECM-IO в одном физическом блоке; передний и задний силовые BCM оставить отдельными **одинаковыми PCB**. Референсы OEM и GitHub: [обзор](research/automotive-architecture-benchmark-20261120.md).

## Обновление после уточнения физической компоновки (20.11.2026)

Один центральный корпус с двумя STM32F405 остаётся предпочтительным кандидатом, но установленная **середина автобуса** (бак, раздатка, VSS, часть тормозных датчиков и аварийная дверь) обосновывает изучение **отдельного MID-IO** вместо длинных чувствительных проводов к CAB. Две универсальные F/R силовые PCB сохраняются. Предложена независимая резервная схема стопов и новые актуаторы дверей, безопасный вариант которых ещё **не выбран**. [Подробный зональный RFC](rfc-zonal-mid-io-brakes-doors-20261120.md).

## 1. Три основных варианта

| Критерий | A. 4 отдельных модуля | B. Всё на одном MCU | **C. Общий передний корпус, 2 независимых STM32** |
| --- | --- | --- | --- |
| Приборы/ввод | CLUSTER + BCM-F-IN отдельно | Монолит | Одна локальная подсистема CAB/Cockpit |
| Gateway | Отдельный | На том же MCU | Второй STM32 в том же корпусе |
| ECM-IO | Отдельный возле двигателя | В монолите | Аналоговые входы в Cockpit **если длины/помехи позволяют**, либо позднее опционный remote engine/sensor node |
| Связь ENGINE + BODY с приборами | 2 CAN/два узла | 2–4 CAN того же MCU | CAB STM32 с **CAN1 ENGINE + CAN2 BODY** напрямую |
| Независимость Gateway | Да | **Нет** | CAB локально работает при отказе Gateway |
| Сложность проводки | Выше, больше коробок | Самая низкая по корпусам | Один центральный корпус и два зональных силовых BCM |
| Отказ общего корпуса/ввода питания | Часть локальной функций сохраняется | Очень большой общий отказ | Общий физический риск есть, смягчать раздельными источниками и независимыми safety-линиями |
| Универсальность разных машин | Высокая | Ограничивается монолитным I/O | Высокая при опциональной секции Engine I/O |
| Рекомендация на текущую фазу | Резервный вариант | **Не рекомендован** | **Предпочтительный кандидат для прототипа** |

**Не считать C автоматически промышленно безопасным**: два MCU в одном корпусе не устраняют общий отказ разъёма, питания, воды, нагрева и основной массы.

## 2. Предлагаемая топология C (не утверждена)

~~~text
                      АКБ/защищённое питание 12/24 В
                  ┌────────────────────────────────┐
                  │ AVTOSTAR CENTRAL — один корпус  │
                  │                                │
 IGN/SWITCHES --->│ MCU-A: COCKPIT/CAB (STM32F405)│
 GAUGE SENSORS -->│   - физические кнопки/входы    │
 ALARM inputs ----│   - измерение RPM/ОЖ/масла     │
 2xVSS -----------│   - interface штатных приборов │
                  │   - оценка КПП/раздатки        │
                  │   - CAN1 ↔ ENGINE CAN          │
                  │   - CAN2 ↔ BODY CAN            │
                  │         | Local diag (CRC)     │
                  │         v                      │
                  │ MCU-B: GATEWAY (STM32F405)      │
                  │   - 2x built-in bxCAN          │
                  │   - 2x SPI MCP2518FD candidate│
                  │   - whitelist ENGINE/BODY/     │
                  │     HOUSE/AUX                  │
                  │       | UART/SPI diag          │
                  │     ESP32: Web / telemetry     │
                  └────────────────────────────────┘
                      |       |        |        |
                  ENGINE    BODY     HOUSE   AUX/4th
                    |         |        |
                   ECU    BCM-F-OUT   HOUSE-IO
                  future  BCM-R-OUT   HOUSE-POWER

  Механический спидометр, аналоговый комбинированный прибор,
  двойной манометр, аварийный выключатель и критичные
  сигнальные лампы: исходные независимые тракты сохраняются.
  Стопы и аварийная сигнализация: отдельная проверенная
  проводная/аппаратная независимая реализация, не только CAN.
~~~

Ключевое: **у MCU-A и MCU-B собственные трансиверы на ENGINE и BODY**, а не один общий PHY. Каждый MCU — узел той же шины. На HOUSE/AUX для MCU-A прямого доступа нет; только разрешённая телеметрия через MCU-B. Локальный интерфейс MCU-A↔MCU-B — для диагностики/конфигурации, **не** единственный путь данных для приборов и кнопок.

**Не делать MCU-A вторым общим межсетевым Gateway.** CAB получает/передаёт свои собственные именованные сообщения из ENGINE/BODY согласно утверждённой матрице, но не пересылает чужие кадры между шинами и не открывает им общий безусловный шлюз. Это важная граница управления даже если один физический MCU подключён к двум сетям.

## 3. Распределение задач между двумя STM32

### MCU-A (STM32F405, блок CAB / Cockpit I/O)

- Клавиши/подрулевые переключатели, замок IGN/START (как диагностический вход; пуск/зажигание — аппаратные цепи).
- Контроль **существующих** контрольных ламп (высокоомное наблюдение); новые лампы только по независимому safety review.
- Приборы: локальное +15/B+, связь с купленным тахометром через формирователь **0–5 В** с проверенной частотой; затем электронный спидометр с проверенным частотным выходом или отдельным VSS.
- Датчики карбюраторного двигателя: защищённый вход RPM (с трамблёра), температура ОЖ, давление масла, аварийные контакты, генератор/зарядка **без разрыва D+/61**.
- Два VSS (раздатка, КПП) для скорости, пробега, передачи и диапазона раздатки. Собственные локальные вычисления; сообщения ENGINE CAN.
- Возможно входы clutch и front axle; фактическое наличие датчика переднего моста на ПАЗ 2001 не подтверждено.
- **CAN1 ENGINE и CAN2 BODY**: сообщает измеренные данные/состояние клавиш, читает ECU/BCM status. Отказ MCU-B не лишает кабину прямого доступа к ENGINE/BODY.
- Собственный watchdog, brownout, безопасная загрузка и самопроверка входов.

### MCU-B (STM32F405, Gateway)

- Два встроенных bxCAN плюс два контроллера SPI-CAN (кандидат MCP2518FD, выбор в отдельном BOM).
- На ENGINE/BODY у него свои CAN-трансиверы — собственный узел, физические шины не соединены без MCU.
- Whitelist событий/телеметрии между ENGINE, BODY, HOUSE, AUX, контроль очередей, bus-off, rate-limits, логи.
- ESP32 подключён к MCU-B и получает только разрешённую телеметрию; по умолчанию доступ только для чтения, защищённый режим сервиса.
- MCU-B может обновляться/отказывать без перезагрузки MCU-A и без отключения приборов/местной кузовной работы.

### BCM-F/R-OUT — без изменений

- Две одинаковые платы с DNP-вариантами, до 24 каналов проектно, силовые ключи с диагностикой.
- Физически у переднего и заднего распределительных узлов. **Не** переносить ламповые токи в центральный корпус/панель.
- Команды света — локальные BODY CAN и отдельные проверенные fail-safe линии по функциям. Самостоятельная диагностика.

### ECM-IO — статус становится опциональным физическим модулем

Его **функции не исчезают**, если удаляем отдельную плату. Они выполняются входной секцией MCU-A. Но если от моторных датчиков, VSS на раздатке/КПП и топливного датчика до кабины длинные/помеховые линии, либо нужна универсальность для заднемоторных машин, можно добавить удалённый ENGINE-IO/Transmission-IO без изменения DBC. Точный выбор — после измерения реальных жгутов. При будущем AVTOSTAR ECU оно получает собственные **прямые** критичные моторные датчики, а CAB переключается на CAN-телеметрию ECU; аналоговые параллельные подключения могут требовать отдельной развязки.

## 4. Примерный бюджет I/O, **не окончательная распиновка**

| Группа | Резерв для MCU-A (эскиз) | Примечания |
| --- | --- | --- |
| Дискретные/резистивные входы кнопок | **24–40 линий контактов** или оптимизированные группы через защищённые IO expanders | На фото 11 видимых клавиш плюс подрулевые, IGN, аварийные контакты; многополюсные выключатели могут потребовать много линий. Нельзя считать «11 клавиш = 11 GPIO» |
| Аналоговые измерения | **8–12 защищённых каналов** | Масло, ОЖ, топливо (если провод идёт сюда), локальное B+, генератор/измерение, резерв; конкретные реостатные схемы согласовать |
| Входы импульсов | **3–4 канала timer capture** | RPM, VSS_TC, VSS_GB, резерв |
| Управление лампами/индикацией | Не менее **9 наблюдаемых** верхних сигнальных окон; output budget после анализа | Не переподключать критичные лампы на MCU без fail-safe |
| Частотные выходы на приборы | **1–2** | купленный тахометр 0–5 В; будущий электронный спидометр согласно его паспорту |
| CAN | **2 встроенных CAN + 2 CAN-трансивера** | CAN1 ENGINE; CAN2 BODY, отдельные разъёмы/фильтры |
| Отладка | SWD, логический UART, optional SPI/I2C | Наличие свободных физических выводов проверять по pinmux и выбранному корпусу F405 |

STM32F405 в корпусе LQFP64 может оказаться слишком ограничен по GPIO и mux для всех функций. Рассмотреть **LQFP100/LQFP144** и отдельные защищённые expanders; выбор корпуса **после** полного I/O budget. Независимые аппаратные аварийные линии вообще не должны занимать обязательные MCU-пины для своей основной функции.

## 5. Приоритеты CAN-данных для приборов — только предложения

| Сигнал | Источник сейчас | Потребитель | Предварительная периодичность |
| --- | --- | --- | --- |
| RPM | CAB по трамблёру → позже AVTOSTAR ECU | CAB локально / ENGINE CAN | 20–50 мс |
| VSS_TC / скорость | CAB по датчику в приводе троса | Приборы/ENGINE CAN | 20–50 мс |
| VSS_GB / передача | CAB | ENGINE CAN/индикация | 20–50 мс при движении |
| Давление масла, температура | CAB → позже ECU | Приборы/ENGINE CAN | 100–250 мс; **аварийные датчики отдельной линией** |
| Состояние входов кузова | CAB | BCM-F/R-OUT BODY CAN | при изменении + периодическое подтверждение 20–100 мс в зависимости от команды |
| Фактические выходы, ток и отказ лампы | BCM-F/R-OUT | CAB | 50–250 мс, события немедленно, stale/timeout |
| House телеметрия | HOUSE-IO | Gateway/ESP32 | 0.5–2 с в зависимости от параметра |

Эти времена не испытаны и **не** нормативы. Должны определяться бюджетом CAN, задержками/очередями, приоритетами, архитектурой аварийных линий и измерением worst-case latency. Для критических ламп время CAN не заменяет прямого аварийного тракта.

## 6. Состояния отказов — обязательные тесты до принятия

| Fault injection | Что должно продолжаться | Что разрешено потерять |
| --- | --- | --- |
| MCU-B остановлен / ESP32 выключен | MCU-A читает датчики/показывает приборы и общается с BCM по BODY; независимые лампы/аварийка/стопы работают | Межсетевая телеметрия HOUSE/AUX, веб-интерфейс и журнал Gateway |
| MCU-A остановлен | Независимое зажигание/аварийное отключение, штатные приборы и критические предупреждения; штатная аппаратная аварийка/стопы | Новые советы переключения, диагностика кнопок, опциональные приборы; функции кузова требуют специально доказанного резервного локального пути |
| CAN ENGINE short/bus-off | Сохраняются локальные измерения, аварийная индикация; BODY работает | Внешние моторные сообщения, ошибочные значения помечены stale |
| CAN BODY short/bus-off | Двигатель/локальная моторная телеметрия продолжает работу; независимый световой fallback | Сетевое управление некоторыми кузовными нагрузками, пока не восстановлено |
| Общий разъём/масса/питание модуля повреждены | Независимые обязательные аварийные цепи в отдельной защищённой ветви | Практически всё некритичное в центральном корпусе |
| Перезагрузка одной MCU | Другая MCU не должна reset-иться; собственное питание/такты/надзор, чёткие startup состояния | Передача данных того MCU на время сбоя |
| Контакт указателя / реостатный датчик повреждён | Критическое предупреждение по отдельному контакту, если требуется; не показывать stale как реальное | Численное невалидное значение |

Одна печатная плата с двумя MCU может иметь общие точки отказа (GND plane, коннектор, ESD, вода). Варианты двух электроизолированных или отдельно защищённых доменов питания, двух плат на backplane и отдельного корпуса Gateway сравнить по фактическим отказам/стоимости. Не объявлять два MCU автоматически резервированием.

## 7. Что требуется решить **перед** замораживанием структуры

1. Сколько реальных клавишных контактов и проводов на панели 2001 года? Точные назначения 9 световых окон, комплектация/клеммы приборов.
2. Точные расстояния и помехи трасс до RPM (катушка/трамблёр), масла, ОЖ, VSS на раздатке и КПП, датчика топлива; где удобнее защищать/оцифровывать.
3. Приборы на первом этапе остаются штатными; будущий цифровой или электронный спидометр и тахометр должны иметь **свои** утверждённые интерфейсы и требования по отказам.
4. Где ставить корпус Central: зад приборным щитком или в отдельном обслуживаемом переднем электрощите? Места, герметичность, вентиляция, температура, быстрый демонтаж.
5. Варианты доступа к входным платам и замены MCU-B без демонтажа MCU-A — важны для ремонтопригодности.
6. Кто предоставляет стабильные и единичные источники ENGINE RPM/VSS/TEMP при добавлении будущего ECU, и кто хранит реальный одометр.
7. Подтвердить, какие именно цепи стоп/аварийка/масло/перегрев/тормоза должны оставаться аппаратными и как будет работать резерв при полном обесточивании Central.
8. Конечный выбор: два MCU на **одной PCB** либо модульная сборка из отдельных логических плат в общем корпусе; это отдельный вопрос manufacturability.

## 8. Предварительное заключение, не ADR approval

**Вариант C рациональнее исходной идеи с отдельным CLUSTER для первого ПАЗ.** Он соответствует реальному расположению приборов и переключателей, использует ровно два независимых STM32 при сохранении четырёх CAN у Gateway, уменьшает количество корпусов и оставляет два зональных силовых блока на общей PCB. **Но** преимущества окончательно подтверждаются только после обмера жгутов, заполнения GPIO budget, анализа единичных отказов и испытаний. Вопрос интеграции ECM-IO физически остаётся открытым, хотя его функциональную роль можно встроить в Cockpit MCU.
